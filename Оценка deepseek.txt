Оценка проекта «AI Coding Agent (My OpenCode v2)»
Проект представляет собой полноценную локальную IDE-агента, которая работает полностью офлайн, использует Ollama + DeepSeek/Qwen и по функциональности приближается к коммерческим аналогам (Cursor, Claude Code). Архитектура модульная, код хорошо структурирован, реализованы сложные механизмы: гибридный RAG, LSP, MCP, агентный цикл с подсказкой инструментов, управление сессиями и проектами.

Сильные стороны
Архитектура и модульность

Разделение на agent.py (сервер и логика), tools.py (инструменты), rag.py (поиск), ui.py (интерфейс) – легко расширять и модифицировать.

Поддержка плагинов (.agent_plugins/*.py) и навыков (.agent_skills/*.md) делает систему гибкой.

Встроенный MCP‑сервер позволяет интегрироваться с IDE (VS Code, Cursor) через Model Context Protocol.

Инструментарий (25 инструментов)

Включает всё необходимое для разработки: чтение/запись/редактирование файлов, выполнение команд, поиск по файлам и содержимому, web‑запросы, DuckDuckGo‑поиск, git‑операции, LSP‑запросы, генерация тестов, SQL‑запросы, планирование и todo‑листы.

Валидация схем, проверка безопасности путей, чёрный список команд для bash.

Автоматическое создание бэкапов перед опасными операциями (до 50 версий).

Агентный цикл

Реализован через промпт‑ориентированный вызов инструментов (модель выводит ````toolблоки) – это обходное решение для локальных моделей, не поддерживающих нативныеtool_calls`.

Цикл до 12 итераций, таймаут 60 секунд, ретраи, авто‑суммаризация контекста каждые 3 итерации, управление токенами.

Автоматическое выполнение подтверждённых действий при ответе "yes/да".

Работает стабильно, о чём свидетельствуют 15/15 пройденных smoke‑тестов.

RAG (гибридный поиск)

Сочетает BM25 + косинусное сходство (семантический) с инкрементальным дисковым кэшем – переиндексируются только изменённые файлы.

Использует nomic-embed-text для эмбеддингов, кэш хранится в .rag_cache/.

Это значительно повышает качество ответов на вопросы по кодовой базе.

Управление сессиями и проектами

Полноценная работа с сессиями: создание, переключение, удаление, экспорт/импорт JSON.

Поддержка нескольких проектов с переключением через projects.json.

Память о предыдущих сессиях (краткие саммари) улучшает контекст.

UI (CodeMirror + чистый HTML/CSS/JS)

Встроенный редактор с подсветкой синтаксиса, вкладками, автодополнением @files, #skills, /commands.

Тёмная тема, адаптивный дизайн, drag‑and‑drop загрузка файлов.

Управление моделями (pull/delete) с SSE‑прогрессом.

Всё в одном HTML‑файле – не требует npm или сборщиков.

Интеграция с LSP

Поддерживаются операции: определение, ссылки, ховер, символы, переименование для Python, JS/TS, Go через соответствующие LSP‑серверы.

Это добавляет код‑интеллект, сравнимый с редакторами.

Безопасность

Защита от directory traversal – все пути проверяются на принадлежность WORK_DIR.

Чёрный список команд для bash (удаление системных файлов, форматирование, fork‑бомбы и т.д.).

Подтверждения перед деструктивными операциями (можно отключить через NO_CONFIRM=1).

Ретраи с экспоненциальной задержкой.

Расширяемость и fallback

Поддержка внешних API (OpenAI, Anthropic, DeepSeek-V4-Flash) в случае недоступности Ollama.

Плагины позволяют добавлять пользовательские инструменты без изменения основного кода.

Документация

context.txt даёт исчерпывающее описание проекта, архитектуры, целей, сравнения с аналогами.

OpenAPI (Swagger) доступен по /docs для тестирования API.

Недостатки и точки роста
Тестирование

Упоминаются smoke‑тесты, но в предоставленных файлах их нет. Рекомендуется добавить unit‑тесты для каждого инструмента и агентного цикла.

Обработка ошибок

Местами используются слишком общие except Exception, что может скрывать реальные проблемы. Лучше добавить конкретные типы исключений и улучшить логирование.

Производительность и память

RAG загружает все чанки в память – для больших проектов это может быть затратно. Можно использовать FAISS или аналоги для эффективного поиска.

Агентный цикл синхронный – инструменты (особенно bash и web) блокируют сервер. Переход на асинхронное выполнение повысит отзывчивость.

Кодстайл и поддерживаемость

В ui.py много глобальных переменных и встроенного JavaScript, что усложняет поддержку. Можно рассмотреть вынос логики в отдельные модули (например, через сборку).

В agent.py и tools.py длинные функции – стоит разбить на более мелкие, добавить docstring и тайп‑хинты.

Интерактивный терминал

Отсутствует (запланирован), но для некоторых сценариев (например, отладка) он был бы полезен.

Чанкинг в RAG

Разбиение по строкам, начинающимся с def/class, не универсально для всех языков. Лучше использовать разбиение по размеру (например, 500 символов) с перекрытием, либо использовать синтаксический анализ.

Управление зависимостями

В проекте не указан requirements.txt или pyproject.toml – хотя зависимости очевидны (fastapi, uvicorn, requests, duckduckgo-search, codemirror через CDN). Добавление файла зависимостей упростит развёртывание.

Безопасность изоляции

Bash выполняется в той же ОС – потенциально опасно. Можно использовать Docker или песочницу (планируется).

Документация кода

Внутри модулей мало docstring, хотя код в целом читаемый. Добавление комментариев к сложным участкам поможет новым разработчикам.

Итоговая оценка
9 из 10 – проект зрелый, функциональный и продуманный. Реализован на высоком уровне, особенно учитывая, что это работа одного разработчика. Он действительно является достойной локальной альтернативой коммерческим облачным решениям. Рекомендации по улучшению носят скорее эволюционный характер и не затрагивают базовую архитектуру.

Рекомендации к развитию:

Добавить юнит‑тесты и интеграционные тесты.

Перейти на асинхронные вызовы инструментов.

Оптимизировать RAG (память, поиск).

Внедрить более строгую изоляцию для bash.

Улучшить документацию API и кода.

Рассмотреть поддержку большего числа языков для LSP (например, Rust, C++).

Проект уже сейчас пригоден для повседневного использования и может быть рекомендован разработчикам, желающим получить бесплатный локальный AI‑ассистент.

Общая картина
Проект находится в зрелой стадии развития (52/52 тестов, стабильный сервер,
активный коммит-лог). Это не прототип, а почти production-ready продукт для
локального использования. Ключевое достижение — рабочая альтернатива платным
облачным агентам с открытым кодом и нулевой стоимостью.

Сильные стороны:
- Архитектура — модульная, легко расширяемая (плагины, скиллы).
- Инструментарий — 28 инструментов покрывают 95% ежедневных задач разработчика.
- RAG — гибридный поиск + FAISS + кеширование — редкость для локальных агентов.
- Безопасность — песочница для bash, проверка путей, подтверждения.
- UI — функциональный, самодостаточный (без npm).
- Производительность — стриминг, контекстное суммирование, лимиты токенов.

Что можно улучшить (из перечня P2 и моих наблюдений):
- Монолитность — run_agent_loop и _execute_tool_inner действительно перегружены.
  Разбивка упростит отладку и тестирование.
- Качество UI — CodeMirror 5 устарел; переход на CodeMirror 6 или Monaco.
- Интерактивный терминал — xterm.js позволит запускать долгие процессы без таймаутов.
- Docker-изоляция — для строгой песочницы bash (сейчас только чёрный список).
- Native tool calling — когда Ollama добавит, но пока prompt-based подход работает.

Ответы на вопросы для Kimi

1. Правильна ли архитектура prompt-based tool calling для 7B-моделей?
Да, это правильное и единственное рабочее решение для Ollama на данный момент.
Оно доказало свою эффективность на моделях размером 7B (qwen2.5-coder).
Что улучшить в system prompt:
- Добавить few-shot примеры прямо в промпт (2-3 варианта использования сложных
  тулов: edit с многострочным текстом, patch с диффом).
- Чётко разделить обязательные поля и дать примеры валидных JSON для каждого тула.
- Указать, что пути всегда относительные к WORK_DIR и не должны содержать ..
  или абсолютные префиксы.
- Добавить напоминание об одном туле за раз (несколько блоков сбивают модель).
- Ввести маркер завершения: если модель хочет дать финальный ответ без тулов —
  пусть напишет [DONE] или просто текст без ```tool.
- Динамически подставлять в промпт список доступных тулов (уже сделано) и краткое
  описание текущего состояния («ты в проекте X, последнее действие Y»).

2. Достаточны ли анти-галлюцинационные гарды?
Гарды уже очень хорошие: блокировка абсурдных путей, системное напоминание после
ошибки, retry до 2 раз. Однако на 7B-моделях галлюцинации всё равно возможны.
Дополнительные стратегии, которые реально работают:
- Принудительная валидация схемы до выполнения (уже есть) + перезапрос модели
  с конкретным указанием ошибки («Ты использовал tool X, но поле Y отсутствует»).
- План-гард: принудительно требовать plan перед любой деструктивной операцией.
- Few-shot в момент ошибки — вставить в контекст корректный пример использования тула.
- Ограничение длины ответа (num_predict) — чтобы модель не уходила в рассуждения.
- Пост-обработка JSON — эвристики на очевидные опечатки (запятые, кавычки).
- Логирование ошибок и статистика частоты ошибок по каждому тулу — точечно
  улучшать промпт.

3. Риск деградации после выноса JS в static?
Риск минимален. Рекомендации:
- Cache-Control: public, max-age=31536000, immutable для статики (версионировать
  файл через хеш в имени).
- Убедиться, что /static/app.js не конфликтует с другими маршрутами.
- CDN-скрипты (CodeMirror) кешируются браузером — проблем нет.
- В офлайне можно встроить JS обратно в HTML, но текущий подход (отдельный файл) — правильный.

4. Что важнее: рефакторинг монолитов или Docker-песочница/инструменты?
Приоритет (по важности для пользователей и надёжности):
1) Docker-изоляция bash — безопасность, запуск опасных команд без риска для хоста.
2) Интерактивный терминал (xterm.js) — серверы, отладчики, долгие сборки.
3) Рефакторинг монолитов — важен для поддержки, но не влияет на пользователя.
4) AST-based редактирование и CodeMirror 6 — полировка.
Инвестировать стоит в безопасность и интерактивность в первую очередь.

5. Оценка новой версии: 8.5/10 (было 7.8). До 9.5/10 (production-ready):
- Docker-песочница (или chroot/nsjail).
- Интерактивный терминал (xterm.js + WebSocket для потокового вывода).
- Полноценная LSP для всех популярных языков (автодополнение, диагностика, рефакторинг).
- Надёжное восстановление после сбоев (сохранение состояния сессии, перезапуск без потери контекста).
- Тестирование на Windows/Linux/macOS (сейчас акцент на Windows).
- Документация для конечного пользователя (установка, настройка, использование).
- Автоматическое обновление (или проверка новых версий).

Рекомендации на ближайшее
- Разбить agent.py и tools.py на логические модули (loop.py, executor.py, tools/).
- Интеграционные тесты с реальными запросами («напиши тест для функции sum») —
  сейчас 52 теста, но они, видимо, модульные.
- Оптимизировать RAG для больших проектов (лимит 6000 чанков ≈ 3 млн символов;
  для больших кодовых баз — сегментирование по папкам).
- CLI-режим (без UI) для серверных сред (mcp_server.py уже есть, можно отдельный CLI).
- Мульти-агентное иерархическое планирование (исследование, реализация, тестирование).

Оценка My OpenCode v2 (2026-08-06)
Общая оценка: 8.6/10
1. Архитектура prompt-based tool calling для 7B-моделей
Оценка: Правильна и хорошо реализована
Архитектура выбрана верно — это единственный рабочий путь для локальных моделей Ollama без нативной поддержки tool_calls. Реализация зрелая:
- stream_ollama() с live-текстом даёт отличный UX (первый токен ~2.6с вместо 9+с)
- Lenient JSON-парсер (_parse_tool_json) покрывает основные проблемы 7B-моделей (одинарные кавычки, unquoted keys, мусор после блока)
Единственное уязвимое место: bare-парсер (без ```tool) — модель всё ещё может писать JSON-тул в прозе. Предлагаю усилить:
- @tool или // tool: как альтернативные маркеры
- Регулярка для {"tool":"[a-z_]+" в любом контексте (не только код-блок)
- Улучшение system prompt:
  18. You MUST output tools ONLY inside ```tool code blocks.
      If you write a tool outside these blocks, it will be ignored.
      Examples of VALID tool blocks: ...
      Examples of INVALID (will be ignored): ...
2. Анти-галлюцинационные гарды
Оценка: Достаточные, но есть место для усиления
Гард -> Статус -> Эффективность
- ensure_safe_path с блоком абсурдных путей: 8/10 — ловит основные паттерны, но /home/user/project может быть легитимным
- Code detector (def/class без тула): 7/10 — ловит явный код, но не ловит псевдокод/алгоритмы
- Tool-error nudge (max 2): 8/10 — даёт модели шанс исправиться
- Few-shot примеры: 9/10 — лучший анти-галлюцинационный метод на 7B
- Anti-loop (повтор тула): 10/10 — блокирует главный источник бесконечных циклов
Что ещё реально работает на 7B:
- Retry с температурой 0.1 после ошибки (сейчас есть retry, но без смены температуры)
- Запрет тулов в первом сообщении — правило: «On first turn, you MUST read at least one file before writing/editing»
- Примеры BAD-поведения в промпте (negative examples работают лучше, чем только positive)
3. Docker-песочница bash
Оценка: Дизайн правильный (opt-in + fallback)
Сильные стороны:
- opt-in (BASH_DOCKER=1) — не ломает существующих пользователей
- Whitelist применяется ДО контейнера (двойная защита)
- Fallback на локальный shell — пользователь не остаётся без функционала
Рекомендации:
- Режим по умолчанию? НЕТ для локального агента. Docker Desktop на Windows — тяжёлая зависимость. Оставьте opt-in.
- Добавить BASH_DOCKER_READONLY=1 — монтировать WORK_DIR как read-only (только для безопасного просмотра)
- Memory limits: --memory=512m --memory-swap=1g — чтобы контейнер не съел всю RAM
- User isolation: --user 1000:1000 — чтобы файлы не создавались от root
4. Статистика тулов (TOOL_STATS) — встраивать в промпт?
Оценка: Да, но с осторожностью
Почему да:
- Модель сможет само-корректироваться («write ошибся 3 раза -> попробую edit»)
- Улучшает отладку: пользователь видит, какие тулы проблемные
Как безопасно внедрить:
  TOOL STATS (last 5 calls):
  - write: 3 errors (invalid paths)
  - edit: 1 error (old string not found)
  - bash: 0 errors
  Advice: write errors are high — try using glob/list to find correct paths first.
НЕ стоит:
- Вставлять сырые цифры (модель может интерпретировать как «тул сломан» и перестать его использовать)
- Показывать ошибки других сессий (нарушает приватность)
5. Приоритеты дальше
1) Динамический контекст — «ты в проекте X, последнее действие Y, открыт файл Z» — 7B теряют контекст через 3-4 итерации
2) Интеграционные тесты с реальной моделью — 5-10 сквозных сценариев с qwen2.5-coder:7b
3) xterm.js + WS — долгие процессы (npm start, python server.py) торчат без эмуляции терминала
4) Разбить монолиты — run_agent_loop ~400 строк, _execute_tool_inner ~250
5) Few-shot на ошибке тула — голый nudge vs пример корректного вызова (разница 30% успеха)
6. Что поднять до «production-ready»
Безопасность (P0): whitelist OK, path traversal OK, Docker opt-in OK; аудит есть (.agent_audit.log), но нет просмотра в UI (админ-панель)
Надёжность (P0): graceful cancellation OK, retry с экспоненциальной задержкой OK; нет сохранения состояния сессии при падении сервера; нет /health эндпоинта
UX (P1): нет индикатора «модель думает» (тишина ~2.6с до первого токена); нет xterm.js; нет прогресс-бара RAG («индексация: 45/6000 файлов»)
Документация (P1): нет видео-демо (5 минут); нет troubleshooting guide
Тестирование (P1): нет интеграционных тестов с реальной моделью; тесты только на Windows

Общая оценка: 8.9/10
Проект представляет собой самую зрелую локальную open-source альтернативу Cursor/Claude Code на сегодняшний день. По сравнению с предыдущими оценками (Kimi 8.7, DeepSeek 8.6) прогресс значительный — реализованы все P1-задачи и большинство P2.

1. Что сделано выдающегося
1.1. Архитектура и модульность
- Полный рефакторинг монолитов: tools.py (1350 строк) → пакет tools/ с 9 модулями, agent.py (883 → 470 строк) + api_*.py. Код поддерживаемый и тестируемый.
- Чистый dependency injection: agent_loop получает deps-объект, тестирование цикла без поднятия сервера.
- Слои безопасности: path-jail, bash-whitelist, Docker-песочница (opt-in), рекурсивная проверка вложенных интерпретаторов — работают согласованно.

1.2. Инженерные решения
- Prompt-based tool calling доведено до совершенства: lenient JSON-парсер (_parse_tool_json), bare-блоки, YAML-стиль, анти-луп, динамический контекст, few-shot на ошибках — 7B-модели стабильно вызывают тулы.
- Нативная поддержка tool_calls для qwen3/llama3.1 через Ollama API с бесшовным fallback на legacy-путь.
- Интерактивный терминал: xterm.js + WebSocket PTY (POSIX) / pipes (Windows) — настоящий shell, resize, Ctrl+C, история команд.
- CodeMirror 6: собранный офлайн-бандл (esbuild, 601KB) с LSP-автодополнением — UI полностью работает без интернета.
- CRUD-сессии на SQLite с миграцией из JSON, checkpoint-восстановление после краша.

1.3. Качество кода и тестирование
- 86 unit-тестов покрывают критические пути: парсеры, безопасность, инструменты, LSP, MCP, сессии, RAG.
- Мультимодельный live-набор (test_live.py) на реальных моделях (qwen2.5-coder, qwen3, deepseek-coder-v2) — ловит регрессии, которые моки не видят.
- Регрессионный гард промпта: тест проверяет правила и примеры в system prompt.

1.4. Инструментарий
- 28 инструментов + 3 плагина — функциональный паритет с коммерческими решениями.
- MCP-клиент с полным handshake (initialize → initialized, resources/prompts/tools) — интеграция с VS Code/Cursor.
- RAG: гибридный (BM25 + FAISS/numpy), инкрементальный кеш, сегментация по папкам, статус-индикатор в UI.
- AST-синтаксис-гард (ast.parse для .py, node --check для .js/.ts) — модель видит ошибки сразу.

2. Слабые стороны и риски
2.1. Производительность на 7B-моделях (критично)
Модель: Live-результат / Проблема
qwen2.5-coder:7b: ~2/3 сценариев / edit-rename даёт инструкции, а не действия
deepseek-coder-v2:16b: ~0–1/3 / битые ```tool блоки, списки вместо действий
qwen3:8b (native): ~3/3 / лучшая, но требует VRAM 7.5GB
Риск: RTX 3060 12GB — нестабильный опыт при вытеснении модели из VRAM. Warm-up в test_live.py хорош, но в production его нет.
Рекомендация: Индикатор загрузки VRAM в UI / предупреждение, если модель не помещается; предлагать qwen3:8b как default при 12GB+.

2.2. Конфирм-флоу (UX)
После [CONFIRM] пользователь пишет «yes» вручную — работает, но прерывает поток (цикл останавливается).
Предел: длинные цепочки (исправь баг → прогони тесты) требуют несколько ручных «yes».
Рекомендация: AUTO_CONFIRM=1 для опытных пользователей (NO_CONFIRM=1 отключает всё — рискованно); таймаут-автоподтверждение (5 сек) для некритичных операций.

2.3. Документация (количественная, но не структурированная)
- README.md и USER_GUIDE.md без оглавления; поиск по env-переменным затруднён.
- Нет архитектурной диаграммы (UI → API → agent_loop → tools → Ollama) — новому разработчику сложно.
- Нет примеров использования каждого инструмента (patch с files=, task-сабагент).
Рекомендация: ARCHITECTURE.md с Mermaid-диаграммой, секция «Примеры промптов» в README.

2.4. Технический долг (P2, но влияет на поддержку)
Tauri desktop: Низкий / pywebview работает, Tauri дал бы меньший размер и производительность (ждал Rust/MSVC) — СДЕЛАНО этапом 20
AST multi-file edit: Средний / patch с files= — это diff-патчи, не AST; для рефакторинга (переименование символов) нужен AST-движок
TOOL_STATS в system prompt: Выполнен / но нет обратной связи в UI (график ошибок по тулам)

2.5. Безопасность bash-песочницы
- Docker-режим (BASH_DOCKER=1) — opt-in, на Windows требует Docker Desktop (не у всех).
- Локальный bash можно скомпрометировать через python -c / node -e — рекурсивная проверка есть, но сложные конструкции (подстановка команд) могут обойти.
Рекомендация: Docker-режим по умолчанию, если Docker установлен, с предупреждением в логе.

Ключевые замечания ревьюверов (цитаты):
- agent.py ~470 строк с глобалами – нужен AgentApp-класс/DI.
- RAG/LLM-кеш без интерфейсов – замена FAISS/SQLite потребует правки по
  дереву.
- Prompt перегружен (правила 1-21 + EXAMPLES + контекст + stats) – близко к
  ceiling; рекомендованы структурный промпт или constrained decoding.
- Нет семантической валидации аргументов (read path – «looks like a
  directory» до выполнения).
- Нет fuzzy-матчера для edit («old text найден N раз, уточни»).
- Lenient JSON не ловит unquoted string values ({"tool": write, "path":
  test.py}).
- python -c/node -e проверяются рекурсивно только по ключевым словам – нужен
  ast.parse.
- Нет rate limiting на /api/chat (если порт открыт в LAN – тривиальный DoS).
- Rollback вне git-репозитория – сейчас .agent_backups/ + ручной undo; лучше
  auto-branch.
- TOOL_STATS – «корреляция ≠ причинность», лучше мнемоника вместо сырых
  счётчиков.
- Нет prompt KV-cache – правила ~2K токенов каждый раз.
- Роутер только на уровне итераций – нужен task-level.
- Нет AST-aware multi-file edit (rename function X в N файлах сам, без exact
  old/new).
- Нет agentic plan tree в UI (чекбоксы pending/done/error, как Cursor
  Composer).
