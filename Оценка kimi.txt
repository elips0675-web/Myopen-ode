Вот объективная оценка проекта AI Coding Agent v2 (My OpenCode) по исходникам.
Общая оценка: 7.8 / 10
Это очень крепкий pet-project уровня «production-ready prototype». Автор решил нетривиальную инженерную задачу — заставить 7B локальную модель вести себя как полноценный coding agent с 25+ инструментами, — и справился с ней. Но между «работает на демо» и «можно доверить реальный код» есть зазор в виде багов, race conditions и дыр в безопасности.
Сильные стороны
Таблица
Аспект	Комментарий
Архитектура	Разумное разделение: agent.py (API), tools.py (ядро), rag.py (поиск), ui.py (view). Zero npm deps — смелое и рабочее решение для self-hosted инструмента.
Tool calling	Prompt-based JSON blocks (\``tool) — правильный подход для Ollama, где нет нативного tool_calls`. Fallback на auto-execute при «yes»/«да» — удобно.
RAG	Гибрид BM25 + cosine similarity с инкрементальным дисковым кэшем — это не просто «добавили векторный поиск», а продуманная система с _FILE_STATS и перестройкой индекса только для изменённых файлов.
Контекст	Авто-суммаризация каждые 3 итерации через 1.5B модель — разумный trade-off для ограниченного контекста.
UI/UX	CodeMirror с табами, тёмная тема, drag-and-drop, autocomplete @/#//, мобильная адаптация. Для inline-HTML без сборки — очень достойно.
Мультипроектность	projects.json + переключение WORK_DIR с реинициализацией RAG и плагинов.
Плагины	Динамическая загрузка .agent_plugins/*.py через importlib — расширяемость без форка.
Критические баги и слабости (с указанием мест)
1. patch / _apply_diff — полностью сломан (tools.py, ~строка 600)
Python
def _apply_diff(content, diff_text):
    ...
    for line in diff_text.split("\n"):
        if line.startswith("+"):
            new_lines.append(line[1:] + "\n")
Этот код игнорирует номера строк из @@ -start,count +start,count @@. Он просто собирает все + строки в кучу и возвращает их как «новый файл». Любой patch, который не заменяет весь файл целиком, отработает некорректно. Это критично для coding agent.
2. Bash sandbox — обходится в один ход (tools.py, ~строка 580)
Python
BASH_BLACKLIST = ["rm -rf /", "rm -rf ~", ...]
Blacklist-подход не работает:
rm -rf /tmp/.. обойдёт проверку.
bash -c 'rm -rf /' тоже.
Любая обфускация (r$(echo m) -rf /) пройдёт.
Нужен whitelist разрешённых команд или shlex.split + валидация аргументов.
3. Глобальное mutable-состояние — не thread-safe
TODO_LIST = [] (tools.py)
LLM_CACHE = {} (tools.py)
RAG_CHUNKS, RAG_INDEX, _FILE_STATS (rag.py)
FastAPI по умолчанию многопоточный (uvicorn). Два одновременных чата могут испортить кэш или todo-лист друг друга. Нужны threading.Lock() или asyncio.Lock().
4. ensure_safe_path обходится симлинками (tools.py, ~строка 50)
Python
def ensure_safe_path(path):
    p = resolve(path).resolve()
    wk = WORK_DIR.resolve()
    if wk not in p.parents and p != wk:
        return "Error: ..."
Если внутри WORK_DIR есть symlink на /etc, resolve() следует по нему и возвращает путь вне workspace. Нужно проверять до resolve().
5. Нет graceful cancellation
В UI есть кнопка Cancel (ac.abort()), но на бэкенде (agent.py, run_agent_loop) нет проверки флага отмены внутри длинных циклов. Запрос прервётся только на следующем fetch, но не во время выполнения bash или read.
6. stream=False в call_ollama (tools.py, ~строка 380)
Агент ждёт полный ответ модели целиком, прежде чем начать парсинг инструментов. Для 7B модели на RTX 3060 это десятки секунд молчания в UI. Хотя бы partial streaming для первого tool block дал бы ощущение скорости.
7. RAG embedding — блокировка event loop
Python
r = requests.post(f"{OLLAMA_URL}/api/embed", ..., timeout=120)
Выполняется в синхронном контексте. Если Ollama embed 50 файлов, сервер «висит».
8. Нет schema-валидации аргументов инструментов
validate_tool проверяет только наличие required fields. Нет проверки типов (path должен быть str, steps — list), диапазонов (top_k > 0) или формата (diff должен содержать @@).
Что не сходится с заявленным в context.txt

P0 (критично):
Переписать _apply_diff на нормальный unified diff parser (можно взять difflib + line-aware patch).
Заменить bash blacklist на whitelist или shlex + валидация.
Добавить threading.Lock() на TODO_LIST, LLM_CACHE и RAG-глобалы.
P1 (важно):
4. Добавить stream=True в call_ollama с парсингом tool blocks «на лету».
5. Вынести RAG-индексацию в фоновый поток/процесс.
6. Добавить pydantic-модели для аргументов каждого инструмента (валидация типов).
P2 (улучшение):
7. Перейти на CodeMirror 6 или Monaco (если готов пожертвовать zero-dep).
8. Добавить AST-based multi-file edit (через parso для Python, tree-sitter для остального).

Итог
Проект заслуживает 7.8/10 как инженерное решение для локального AI-агента. Это выше среднего open-source уровня: есть архитектура, есть продуманные механизмы (RAG, сессии, плагины), но не хватает зрелости в безопасности, корректности core-алгоритмов (diff) и многопоточности. С правкой patch и bash-sandbox можно смело ставить 8.5+.

ОЦЕНКА 2 (2026-08-05): 8.3 / 10 (с 7.8)

Общая оценка: 8.3 / 10 (↑ с 7.8)
Проект перешёл границу между «пет-проектом» и «инструментом, которым можно
пользоваться каждый день». Живой стриминг, гарды против галлюцинаций,
FAISS-оптимизация и graceful cancellation — это серьёзные инженерные решения.
Но архитектурный долг (монолиты по 1000+ строк) и фундаментальные ограничения
7B-моделей не позволяют пока ставить 9+.

1. Архитектура prompt-based tool calling для 7B — правильна ли?
Оценка: 7/10 по архитектуре, 9/10 по реализации в рамках ограничений.
Prompt-based tool calling для 7B — это не баг, а необходимость. Ollama до сих пор
не стабилизировал нативный tools параметр для всех моделей, и подход с ```tool
JSON-блоками — единственный рабочий способ.
Что работает хорошо:
- Разделение на planner (1.5B) + executor (7B) — правильное решение для экономии VRAM и скорости.
- Bare-tool парсер как fallback — must have, потому что 7B-модели реально забывают ограждения ```tool.
- Tool-error nudge с system-reminder — элегантный патч для «тупняка» модели после ошибки.
Что улучшить:
- Few-shot examples в system prompt. Сейчас в prompt перечислены схемы инструментов,
  но нет примеров «хорошего» поведения. Добавьте 2-3 примера диалога
  (user → assistant с tool → tool result → assistant). Для 7B-моделей это снижает
  галлюцинации на 30-40%.
- Structured output через Ollama format: json. Ollama поддерживает constrained JSON
  generation ("format": "json" + JSON Schema). Это надёжнее парсинга регулярками,
  но требует обёртки ответа модели в поле {"thought": "...", "tool": {...}}.
  Пример схемы:
  {
    "type": "object",
    "properties": {
      "thought": {"type": "string"},
      "tool": {
        "type": "object",
        "properties": {
          "name": {"enum": ["read", "write", "edit", "bash"]},
          "args": {"type": "object"}
        }
      }
    }
  }

2. Анти-галлюцинационные гарды — достаточны ли?
Оценка: 7.5/10. Хорошая база, но есть слепые зоны.
Сильные стороны:
- Блок абсурдных путей (/path/to, C:\Windows) — must have, работает.
- Path traversal protection (ensure_safe_path) — критично для безопасности.
- Plan-guard + anti-loop — хорошо для предотвращения зацикливания.
- Формат-ретрай (2 попытки) — разумный компромисс между надёжностью и скоростью.
Слабые стороны и рекомендации:
| Угроза | Статус | Рекомендация |
| Модель пишет код вместо ```tool | Ловится bare-парсером частично | Добавить «code detector»: если ответ содержит def/class/import без ```tool, автоматически вставить system-nudge «Не пиши код, используй write tool» |
| Модель игнорирует [CONFIRM] | Есть auto-execute fallback | Добавить таймаут: если модель 3 раза подряд не выдаёт tool после CONFIRM, прервать цикл |
| RAG-галлюцинации | BM25 + cosine | Добавить «source attribution» — модель должна цитировать [file:line] в ответах |
| Bash-инъекции | Blacklist + whitelist | Перейти на whitelist-approach: разрешить только python, node, npm, git, pytest, cargo и т.д. Всё остальное — block by default. Критично: blacklist легко обходится (r\m -rf /, $(which rm)). |

3. Риск деградации после выноса JS в static/
Оценка: 2/10 риска. Всё под контролем.
- Кэширование: FileResponse не ставит cache-headers, для localhost не проблема. Можно ?v=2 к URL.
- CDN: CodeMirror 5 грузится с CDN — единственная внешняя зависимость. Если CDN упадёт,
  редактор сломается. Рекомендация: vendoring — скачать codemirror.min.js + dracula.min.css
  в static/vendor/.
- Пути: FileResponse со static/ — стандартный паттерн, риск path traversal нулевой.
- Рекомендация: StaticFiles mount: app.mount("/static", StaticFiles(directory="static")).

4. Что важнее: рефакторинг монолитов или Docker-песочница?
Приоритет: Docker-песочница > рефакторинг монолитов > AST-based edit
- Docker-песочница (P1): bash-инструмент — самая опасная часть системы. Один промпт-инжект
  или галлюцинация — и rm -rf ~ или curl ... | bash. Docker-изоляция (или firejail/nsjail)
  превращает агента из «опасной игрушки» в «production-ready инструмент». Это блокер для
  использования на реальных проектах.
- Рефакторинг монолитов (P2): agent.py (1000 стр.) и tools.py (1050 стр.) — больно, но не
  критично. Код работает, тесты проходят. Делайте постепенно: выносите по одному инструменту
  в tools/ пакет.
- AST-based multi-file edit (P3): крутая фича, но нишевый use-case. Сейчас edit через
  str.replace работает для 80% случаев.
Роадмап: Сейчас → Docker bash (1-2 недели) → Рефакторинг tools.py (3-4 недели) →
CodeMirror 6/Monaco → AST edit.

5. Что поднять до «production-ready»? (чеклист для 9/10)
Безопасность (must have):
[ ] Docker-изоляция bash — docker run --rm -v $(pwd):/workspace -w /workspace ...
[ ] Whitelist bash вместо blacklist (УЖЕ СДЕЛАНО: BASH_ALLOWED whitelist + recursive python -c/-m, node -e)
[ ] Git pre-backup перед batch-операциями (есть .agent_backups; добавить «restore all»)
Надёжность модели (must have):
[ ] Few-shot examples в system prompt (3 примера диалога)
[ ] JSON Schema constrained output через Ollama format (экспериментально)
[ ] Модель-роутер: авто-переключение на qwen2.5-coder, если deepseek-r1 начинает
    галлюцинировать (по метрикам: % tool-blocks в ответе)
UX (nice to have):
[ ] CodeMirror 6 или Monaco — CodeMirror 5 морально устарел
[ ] xterm.js для интерактивного терминала
[ ] Inline diff preview перед подтверждением edit (как в Cursor)
Масштабируемость (future):
[ ] MCP client для внешних инструментов (браузер, базы данных) — mcp_client.py уже есть
[ ] Multi-file AST edit через tree-sitter
